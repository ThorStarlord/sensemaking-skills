# v0.3 External Golden-Path Qualification Protocol

**Status:** FROZEN PROTOCOL — P11 qualification authority  
**Effective:** 2026-09-09  
**Applies to:** Sensemaking Skills v0.3 release qualification  
**Purpose:** define, before execution, what constitutes a valid external golden-path attempt and what evidence is required to claim v0.3 readiness.

This protocol is intentionally stricter than ordinary dogfood. It prevents a failed run from being repaired in place and later described as an uninterrupted product success.

## 1. Qualification claim

A passing attempt supports only this bounded claim:

> One exact Sensemaking Skills release candidate completed the canonical Campaign golden path on one frozen external repository through one real supported coding-agent harness, with deterministic reconstruction, no manual Campaign/artifact repair, and no prior conversation memory supplied to the fresh-context agent.

A pass does **not** prove:

- every repository is supported;
- every coding-agent harness is supported at runtime;
- every Skill will be selected correctly;
- validator success establishes semantic truth;
- capability availability establishes authority;
- the Campaign controller is a semantic router;
- fresh-context agents will always make the same semantic decision.

## 2. Required attempt manifest

Before substantive execution begins, create an immutable attempt manifest containing all fields below. A missing required field makes the attempt **INVALID**, not PASS.

```yaml
protocol: v0.3-external-golden-path-v1
attempt_id: <unique-id>
started_at: <UTC timestamp>

sensemaking_candidate:
  commit_sha: <40-hex>
  tree_sha: <40-hex>
  wheel_filename: <name>
  wheel_sha256: <64-hex>
  version: <candidate version>

runtime:
  os: <name/version>
  python: <version>
  harness: <claude|codex|opencode|other-explicit-supported-harness>
  harness_version: <version-or-explicitly-unavailable>
  adapter_target: <P10 target>
  adapter_scope: <user|project>

external_target:
  repository: <owner/name-or-canonical-url>
  branch: <branch>
  commit_sha: <40-hex>
  tree_sha: <40-hex>
  engineering_goal: <bounded owner-supplied goal>

campaign:
  campaign_id: <id>
  workspace: <path>
  workspace_outside_target_repo: true

operator_policy:
  manual_campaign_repair_allowed: false
  manual_artifact_repair_allowed: false
  manual_validator_output_repair_allowed: false
  prior_chat_supplied_to_fresh_agent: false
```

The manifest is frozen before repository diagnosis begins. If the Sensemaking candidate or target repository changes, the attempt is not silently updated; start a new attempt.

## 3. Target eligibility

The target must be a real repository other than `ThorStarlord/sensemaking-skills`.

It should have:

- non-trivial source code;
- a bounded engineering problem that can reasonably produce a real implementation or analysis result;
- some ordinary validation surface such as tests, build, static checks, or an existing executable behavior;
- no requirement for hidden prior conversation knowledge;
- a frozen commit/tree for the duration of the attempt.

The task must be bounded enough that a failure can be attributed and inspected. "Redesign the whole repository" is not an eligible qualification goal.

## 4. Distribution boundary

The attempt must start from the built candidate distribution, not an editable install.

Required setup:

```text
build exact candidate wheel
→ compute wheel SHA-256
→ create fresh environment
→ install wheel
→ execute from a working directory outside the Sensemaking source checkout
```

The qualification runtime must not rely on repository-root Sensemaking files being available accidentally.

In particular:

```text
campaign ingest
```

must run without `--framework-root` during the golden path.

An explicit framework checkout may be used only in a separate development/debugging episode after an attempt has already failed. It cannot be introduced mid-attempt to rescue qualification.

## 5. Harness boundary

P10 installation proves only that Skill bytes were copied to the declared discovery root. P11 must separately establish that a **real harness runtime** observed/invoked the intended Skill.

Required distinction:

```text
Skill copied to discovery root
!= harness observed Skill
!= Skill selected
!= execution authorized
```

A qualifying attempt therefore records both:

1. the deterministic P10 adapter/install result; and
2. real harness evidence that `repo-sensemaker` was invoked through that harness's Skill mechanism.

Filesystem inspection alone cannot satisfy item 2.

## 6. Canonical golden path

A PASS attempt must traverse the following product path without manual repair:

```text
start
→ repository diagnosis
→ validated artifact admission
→ agent-authored responsibility/authority decision
→ capability inspection
→ bounded work
→ durable evidence
→ reconciliation / repair verification
→ explicit reconciliation disposition
→ durable transition
→ lineage inspection
→ handoff
→ fresh-context resume
→ justified continuation or terminal stop
```

The steps below define the evidence required for each boundary.

### 6.1 Campaign initialization

Use the installed CLI to create the Campaign. Record outputs from:

```text
campaign init
campaign status
campaign validate
campaign history
```

The workspace must remain outside the target repository.

### 6.2 Repository diagnosis

Invoke the real agent-native `repo-sensemaker` Skill through the selected harness against the frozen external target.

The legacy/simple Python `repo_sensemaker.py` path does not satisfy this requirement.

Expected primary artifact:

```text
repository_sensemaking_brief
```

The artifact must be produced by ordinary Skill execution, not hand-authored to satisfy the validator.

### 6.3 Artifact admission

Run installed-distribution ingestion:

```text
campaign ingest
  --workspace <campaign>
  --artifact <brief>
  --target-repo <frozen target>
```

Do **not** pass `--framework-root`.

Required evidence:

- validator returned a normal canonical result;
- admitted artifact ref;
- admission receipt ref;
- artifact SHA-256;
- router SHA-256;
- selected validator SHA-256;
- Campaign reconstruction exposes the artifact and receipt as evidence.

A validator infrastructure error is a product failure for this attempt, not evidence that the artifact is semantically invalid.

### 6.4 Agent-authored responsibility and authority

The active agent interprets the admitted diagnosis and authors the next warranted responsibility using the existing P5 decision contract.

Required evidence records:

- explicit responsibility statement;
- explicit authority state;
- success conditions;
- cited durable evidence;
- committed transition/state.

Deterministic code must not infer the responsibility from artifact prose.

### 6.5 Capability inspection

The agent supplies its responsibility classification to:

```text
campaign capabilities
```

Record the deterministic unranked candidates and their availability/authority metadata.

The agent then independently selects a capability, selects ordinary coding instead, or honestly stops. The registry must not emit a recommended/best capability.

### 6.6 Bounded engineering work

Perform one real bounded work episode against the target repository under the authority already recorded.

Capture ordinary engineering evidence where applicable:

- source diff or analysis artifact;
- tests/build/static-check outputs;
- relevant repository state before/after;
- capability output artifact when a registered capability is used.

Qualification must not introduce a P11-only execution backdoor.

### 6.7 Reconciliation / repair verification

Produce the ordinary reconciliation artifact appropriate to the work:

```text
reconciliation_report
```

and/or:

```text
repair_verification_report
```

Admit it through the canonical P4 boundary.

Before disposition, `campaign reconciliation` should mechanically report that an explicit disposition is required for newly admitted reconciliation evidence.

### 6.8 Explicit disposition

The active agent evaluates the reconciliation evidence and explicitly chooses one existing P5 action:

```text
advance
or defer
or close
```

The exact reconciliation artifact must be cited as transition evidence when it materially supports the decision.

After the committed P8-bound transition, `campaign reconciliation` may report `disposition_recorded` only in the narrow P9 sense: an exact admitted report was explicitly consumed by a committed Campaign transition.

It must not claim the report was correct or semantically sufficient.

### 6.9 Lineage inspection

Run:

```text
campaign lineage
```

The output must mechanically connect, where P8 contracts apply:

```text
exact evidence bytes
→ provenance/admission
→ explicit consumption receipt
→ committed transition
```

No chat transcript may be needed to explain which exact evidence bytes a transition consumed.

### 6.10 Handoff

Generate the ordinary P7 handoff from the current valid Campaign.

Record:

- handoff ref/path;
- reconstruction binding;
- current Campaign state identity;
- any explicitly authored handoff guidance.

The handoff must not invent a semantic next action.

## 7. Fresh-context boundary

After the handoff is generated, the original semantic context ends.

The fresh-context agent may receive only:

- the frozen target repository/worktree;
- the Campaign workspace;
- the installed Sensemaking Skills candidate;
- the handoff reference if needed to locate the workspace artifact;
- ordinary owner goal/context already durably represented by the Campaign/target repository.

It must **not** receive:

- the prior chat transcript;
- a private summary of the prior agent's reasoning;
- unstored instructions describing what the previous agent "really meant";
- copied hidden scratchpad/reasoning;
- manual explanation of which semantic decision it should make next.

The fresh agent reconstructs using ordinary product surfaces such as:

```text
campaign resume
campaign status
campaign history
campaign lineage
campaign reconciliation
```

It then independently decides whether to continue, defer, request owner input, or terminate.

A legitimate `evidence_insufficient`, `owner_decision_required`, `authority_boundary_reached`, or other honest stop may satisfy this step if warranted. Qualification does not require forcing additional work.

## 8. Prohibited manual repairs

Any of the following during an active attempt makes it **FAIL**:

- editing `campaign-state.yaml` by hand;
- editing transition files by hand;
- editing trace/history to make reconstruction pass;
- editing admission receipts;
- editing P8 lineage/consumption receipts;
- editing the handoff or its binding to make resume pass;
- changing validator JSON/output manually;
- replacing a failed artifact with a hand-repaired artifact while pretending it is the same run;
- adding a Sensemaking source checkout or `--framework-root` to rescue installed ingestion;
- giving the fresh agent prior-chat reasoning after the fresh-context boundary.

Product repair is allowed **after** recording the attempt as failed. The repaired product must receive a new candidate SHA/tree/wheel digest and the qualification must restart as a new attempt.

## 9. Operator assistance that is allowed

The operator may perform non-semantic environmental actions that an ordinary user would reasonably perform, provided they are recorded, for example:

- provide credentials already required by the target repository/harness;
- install declared external runtime dependencies;
- start an ordinary test service required by the target project;
- approve an authority-gated action when the Campaign explicitly requires owner authorization;
- answer a genuinely new owner-decision question.

Operator help must not rewrite durable product state or smuggle prior-agent semantic reasoning across the fresh-context boundary.

## 10. Attempt outcomes

### PASS

All required golden-path boundaries complete; deterministic reconstruction succeeds; no prohibited repair occurred; a real harness invoked the Skill; and the fresh agent reconstructed without prior-chat memory.

### FAIL

The frozen candidate encounters a product/harness/packaging/UX defect or requires prohibited manual repair to continue.

A FAIL is useful evidence. Preserve it and start a new attempt only after a bounded product repair.

### INVALID

The attempt cannot support a qualification conclusion because a frozen input changed or required identity/evidence was never captured, for example:

- target SHA changed mid-run;
- candidate SHA/wheel changed mid-run;
- attempt manifest was not frozen before substantive execution;
- runtime/harness identity is unknowable and required by the protocol;
- external event corrupted the run such that product behavior cannot be adjudicated.

INVALID is neither PASS nor product failure.

## 11. Repair taxonomy after FAIL

Classify the blocker before changing the product:

1. **Mechanical product defect** — CLI, persistence, reconstruction, validation, packaging, path, digest, or deterministic contract.
2. **Harness integration defect** — copied Skill was not discoverable/invokable in the real selected harness.
3. **Documentation/UX defect** — ordinary product usage cannot be inferred from the shipped interface/docs without private coaching.
4. **Semantic uncertainty** — the active agent honestly lacks evidence/authority to proceed. This is not automatically a product defect.
5. **External target/environment defect** — unrelated infrastructure prevents adjudication; classify FAIL or INVALID according to whether product behavior was actually tested.

Every product fix must add a regression proof where mechanically testable, receive full exact-head Validator Ecosystem qualification, and produce a new attempt identity.

## 12. Required PASS evidence package

A successful attempt must preserve enough durable evidence to audit the claim without the original chat:

```text
attempt manifest
Sensemaking candidate SHA/tree
wheel filename + SHA-256
runtime/harness identity
P10 setup result
real harness Skill invocation evidence
external target SHA/tree + goal
Campaign initialization/status/validation/history
repository_sensemaking_brief identity
artifact admission receipt + validator provenance
responsibility/authority transition
capability-inspection output
bounded-work evidence
reconciliation/repair-verification artifact + admission
explicit disposition transition
lineage output
handoff + reconstruction binding
fresh-agent resume/reconstruction evidence
fresh-agent continuation/terminal decision
final Campaign validation/status
```

Evidence may be stored in the Campaign workspace, target qualification folder, or repository qualification record as appropriate, but references must be explicit and immutable enough to audit.

## 13. Final release gate

One PASS attempt is necessary but not by itself sufficient to publish.

After PASS:

1. freeze the final release candidate bytes;
2. reconcile version to `0.3.0` consistently;
3. update README/STATUS/productization plan/CHANGELOG/publishing docs;
4. build wheel + sdist;
5. run distribution metadata checks;
6. run the complete exact-head Validator Ecosystem;
7. verify no late review findings;
8. mark the P11 PR ready only after all release evidence is recorded.

Merge and release remain separate authorization boundaries.

The final P11 stop marker is:

```text
P11_EXACT_HEAD_QUALIFIED
```

The release claim after exact candidate integration and publication verification is:

```text
V0.3_GOLDEN_PATH_PASS
```

Neither marker may be produced from CI alone without the real external/harness attempt required by this protocol.
