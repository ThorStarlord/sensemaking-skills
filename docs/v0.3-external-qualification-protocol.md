# v0.3 External Golden-Path Dogfood Protocol

**Status:** NON-BLOCKING POST-RELEASE DOGFOOD PROTOCOL  
**Effective:** 2026-09-09  
**Applies to:** empirical runtime validation of Sensemaking Skills v0.3.x  
**Release authority:** NONE — this protocol does not gate v0.3.0 publication

This protocol preserves the stronger external-runtime experiment designed during P11, but it is no longer part of the v0.3.0 release definition of done. The v0.3 release claim is intentionally narrower and mechanically qualified from the installed distribution.

## 1. Why this is non-blocking

The productization program uses the default loop:

```text
implement
→ validate deterministically
→ dogfood
→ repair observed friction
→ ship
```

The original P11 protocol accidentally made a stronger empirical claim mandatory before shipping:

> one exact candidate must complete the entire Campaign lifecycle on one external repository through one real coding-agent harness and a genuinely fresh agent context.

That remains useful evidence, but it is not required to support the narrower v0.3.0 release claim.

The release therefore distinguishes:

```text
mechanically qualified installed Campaign control layer
!= real-harness Skill discovery qualification
!= universal external-repository success
!= fresh agent semantic-quality guarantee
```

## 2. v0.3.0 release claim — outside this protocol

The blocking release claim is:

> Sensemaking Skills v0.3.0 provides an installable, mechanically qualified Campaign control layer for durable engineering sensemaking: validated evidence admission, explicit agent-authored decisions, capability inspection, reconciliation reconstruction, exact evidence lineage, and integrity-bound handoff/resume. Harness adapters install Skills into declared coding-agent discovery locations; runtime Skill discovery and end-to-end external-repository performance are not part of the v0.3.0 qualification claim.

The blocking release gates live in `docs/productization-v0.3.md`, the Validator Ecosystem, and the release-candidate distribution workflow.

## 3. What this protocol can establish later

A passing dogfood attempt supports only this bounded additional claim:

> One exact Sensemaking Skills distribution completed the canonical Campaign golden path on one frozen external repository through one real supported coding-agent harness, with deterministic reconstruction, no manual Campaign/artifact repair, and no prior conversation memory supplied to the fresh-context agent.

A pass does **not** prove:

- every repository is supported;
- every coding-agent harness discovers or invokes Skills correctly;
- every Skill will be selected correctly;
- validator success establishes semantic truth;
- capability availability establishes authority;
- a fresh agent will make the same or best semantic decision;
- the Campaign controller is a semantic router.

## 4. Required attempt manifest

Before substantive dogfood execution begins, freeze an immutable attempt manifest:

```yaml

attempt_id: <unique-id>
started_at: <UTC timestamp>

sensemaking_candidate:
  commit_sha: <40-hex>
  tree_sha: <40-hex>
  distribution_filename: <wheel-or-published-version>
  distribution_sha256: <64-hex-or-published-artifact-identity>
  version: <version>

runtime:
  os: <name/version>
  python: <version>
  harness: <claude|codex|opencode|other-explicit-compatible-harness>
  harness_version: <version-or-explicitly-unavailable>
  adapter_target: <P10 target>
  adapter_scope: <user|project>

  repository: <owner/name-or-canonical-url>
  branch: <branch>
  commit_sha: <40-hex>
  tree_sha: <40-hex>
  engineering_goal: <bounded owner-supplied goal>

  campaign_id: <id>
  workspace: <path>
  workspace_outside_target_repo: true

  manual_campaign_repair_allowed: false
  manual_artifact_repair_allowed: false
  manual_validator_output_repair_allowed: false

```

If the Sensemaking candidate or target changes, start a new attempt. Never edit a failed attempt in place into a PASS.

## 5. Target eligibility

The target should be a real repository other than `ThorStarlord/sensemaking-skills`, with non-trivial source code, a bounded engineering goal, and an ordinary validation surface such as tests, build checks, static analysis, or executable behavior.

The target commit/tree remains frozen for the attempt.

## 6. Distribution boundary

Run from an installed distribution, not an editable Sensemaking checkout:

```text
install exact distribution
→ execute outside Sensemaking source checkout
→ campaign ingest without --framework-root
```

A separate framework checkout may be used only after an attempt has already failed, for debugging. It cannot rescue the attempt.

## 7. Harness boundary

P10 installation proves only deterministic placement of Skill bytes.

```text
Skill copied to discovery root
!= harness observed Skill
!= Skill invoked
!= execution authorized
```

A dogfood PASS therefore records both the P10 installation result and real harness evidence that `repo-sensemaker` was invoked through the harness's native Skill mechanism. Filesystem inspection alone is insufficient for this optional stronger claim.

## 8. Canonical dogfood path

A complete dogfood attempt may traverse:

```text
start
→ repository diagnosis
→ validated artifact admission
→ agent-authored responsibility/authority decision
→ capability inspection
→ bounded work
→ durable evidence
→ reconciliation / repair verification
→ explicit reconciliation disposition
→ durable transition
→ lineage inspection
→ handoff
→ fresh-context resume
→ justified continuation or terminal stop
```

Each semantic transition remains agent-authored. Deterministic machinery records and validates representation/provenance; it does not infer semantic next action.

## 9. Fresh-context boundary

After handoff, the original semantic context ends. A fresh agent may receive only durable/product inputs such as the target repository, Campaign workspace, installed distribution, and handoff reference.

Do not provide the old chat transcript, a private reasoning summary, or manual coaching that substitutes for Campaign state if the attempt intends to support the stronger fresh-agent claim.

## 10. Outcomes

Classify each dogfood attempt as:

- **PASS** — the declared optional external claim was demonstrated without prohibited repair;
- **FAIL** — a product/runtime defect or manual-repair requirement blocked the declared path;
- **INVALID** — frozen inputs/boundaries were violated or required evidence is missing.

An honest Campaign terminal state such as `evidence_insufficient`, `owner_decision_required`, or `authority_boundary_reached` may still be a valid product outcome; whether it satisfies a particular dogfood goal must be recorded explicitly.

## 11. Relationship to release work

This protocol is deliberately **non-blocking** for v0.3.0.

Its results may inform:

- v0.3.1 repairs;
- harness-specific documentation;
- future runtime-availability detection;
- v0.4 product claims;
- stronger empirical qualification if later product pressure warrants it.

Do not delay a mechanically qualified v0.3.0 release merely to complete this protocol.
