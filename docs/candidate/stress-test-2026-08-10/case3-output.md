Both questions are, at bottom, the same shape: *"we don't yet know something true about actual system behavior, and finding out requires looking somewhere Diagnose hasn't looked yet."* One instance called that empirical; the other called it repository-evidence-not-yet-searched. Both readings are individually defensible — Case 3's subagent gave a coherent argument (searching existing logs is a read operation, not a new experiment) — but applied to structurally similar cases, this is a genuine, observed inconsistency in how `uncertainty.source`'s four-way taxonomy gets applied at the boundary between "static repository content" and "operational/runtime history."

**Consequence for the classification**: the higher-level behavioral discipline (never let the owner substitute for evidence-gathering; separate resolved facts from open recommendations) held cleanly in both cases — that's real, replicated evidence for KEEP. But the specific four-value `uncertainty.source` enum, and in particular the repository_evidence/empirical boundary for questions about operational history rather than static code, is underspecified enough that two runs of the same architecture split an analogous case two different ways. That's evidence toward REVISE for the taxonomy's documentation/definition, not toward DROP or KEEP-as-is — the field is doing real work, but its category boundaries need sharper definition than "repository_evidence vs. empirical" currently gives, specifically for "has X already happened" questions where X is about runtime/operational state rather than source code.
