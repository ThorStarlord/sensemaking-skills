# MAINTENANCE — keeping the semantic control map cheap and safe

The map (`SEMANTIC-CONTROL-MAP.md`) is a candidate for persistence. Persistence
is only justified if the map can be kept correct at low cost. This file
specifies how, using **only machinery the repository already has** — no new
infrastructure (`00-SCOPE.md` boundary).

---

## 1. The derived-fact / judgment split

Every row carries a `Deriv` tag. The three classes are maintained differently.

### `MECH` — mechanically derivable (~24 of 38 rows, ~63%)

A row is `MECH` when a script over existing repo machinery could regenerate its
factual content. These are **refreshed, not re-decided**.

| Row group | Existing machinery that already computes / could compute it | Refresh cost |
|---|---|---|
| SL1–SL5, SL9 (ADR lifecycle: Accepted / Proposed / Superseded / stale-Accepted / merge-pending) | `scripts/probe_relationships.py` already reads every `docs/adr/NNN-*.md` `**Status**` line and cross-refs "Depends on" notes. Add: flag an ADR whose `**Status**: Accepted` is named as superseded in a newer ADR's depends-on list (catches SL1). | seconds; already in the Probe Engine |
| SE6, SA8 (registry mirror drift) | `diff skills/workflow-planner/references/workflow-registry.yaml src/sensemaking_skills/defaults/workflow-registry.yaml`; likewise the two `artifact-contracts.yaml`. `enforcement-contract.md` §6 already frames the "no canonical declared" fact. | one `diff` per pair |
| SE1, SE2, SA13 (what actually runs in CI; `test_path_drift` RED; which branch holds the gate) | parse `.github/workflows/validation.yml` for `pytest` invocations; `git branch -a --contains` for `feat/enforcement-gate`; run `pytest tests/test_path_drift.py -q` for the RED count. `enforcement-contract.md` §1-5 already narrates it. | one workflow parse + one test run |
| SA10, SR3 (canonical vocab + fog-taxonomy doc conflict) | `test_path_drift.py` + a grep of `docs/HARDENING_STATUS.md` vs `docs/canonical-vocabulary.yaml` for taxonomy size | grep + existing test |
| SA12 (version authority) | `enforcement-contract.md` §4-5 + the probe's `conflicting_values` output + `pytest tests/test_cli.py::test_cli_version` | existing probe + one test |
| SE10 (vendored skill drift) | read `distribution-drift.yaml` (already generated) | `cat` |
| SL6, SL7, SL8, SL10, SE5, SE7, SA9, SR1, SR2, SR4, SR-neg | `grep` for a symbol / import / doc name; read a named ADR or plan section | grep, seconds |

**Refresh procedure for `MECH` rows** (run on the staleness triggers in §3):

```
1. probe:   python scripts/probe-repo.py            # ADR lifecycle, relationships
2. diff:    diff the two workflow-registry.yaml; diff the two artifact-contracts.yaml
3. ci:      grep -n 'pytest' .github/workflows/validation.yml
            git branch -a --contains <feat/enforcement-gate tip>
4. reds:    pytest -q tests/test_path_drift.py tests/test_cli.py::test_cli_version
5. drift:   cat distribution-drift.yaml
6. greps:   the ~10 symbol/import/doc-name checks listed per row in the map
7. update only the changed cells; note the date + commit in a change log line
```

No judgment is exercised in steps 1–7. If a `MECH` cell changes, the change is
mechanical fact, not a re-decision.

### `JUDG` — irreducible human/model judgment (~7 of 38 rows, ~18%)

`SA1` (control-loop policy-vs-impl), `SA4` (routing "largest divergence" framing),
`SE8` (is the missing `unevaluable` verdict a *gap*), `SE9` (control-loop
unenforced *by design*), `SR3` (fog taxonomy "de-authorized" framing). These
**cannot be regenerated by a script** — they are architectural interpretations.

**Maintenance for `JUDG` rows:** reviewed by a competent agent/human **only when
a §3 trigger fires that plausibly touches them**, not on a calendar. Each `JUDG`
cell records the reasoning and the date it was last affirmed. A `JUDG` row that
two competent reviewers disagree on (as V1 and agent B disagreed on SA1) is
marked `contested` and keeps both readings — it is not silently resolved.

### `MIX` — mechanical fact + judgment overlay (~7 of 38 rows, ~18%)

E.g. `SA6`: `warrant_enabled=False` is `MECH` (grep); "policy canonical vs
runtime opt-in is a tension" is `JUDG`. `SA8`: "copies drifted / no file
declares canonical" is `MECH`; "this is a problem" is `JUDG`. Refresh the
mechanical half on triggers; re-affirm the judgment half only when the
mechanical half changes materially.

## 2. Where the map physically lives (not decided here)

Candidate: a single `docs/semantic-control-map.md` (the owner's suggestion), or
keep it under `experiments/` until an independent second construction and light
normal-use consultation justify canonical placement. **This prototype does not
create the `docs/` file.** If it ever moves there, the `MECH`/`JUDG` split and
the change-log discipline move with it.

## 3. Staleness triggers (when to refresh — not a calendar)

Refresh the affected rows when any of these happen (all detectable from ordinary
repo activity):

| Trigger | Rows to refresh |
|---|---|
| any `docs/adr/` file added or its `**Status**` line edited | SL1–SL5, SL9, SA1, SA4, SA5, SA7, SA11 |
| any change to `.github/workflows/validation.yml` | SE1, SE2, SE7, SA13 |
| `feat/enforcement-gate` (or its successor) merges | SE1, SE2, SA13, SA9 |
| either `workflow-registry.yaml` or either `artifact-contracts.yaml` edited | SA2, SA8, SA9, SE3, SE4, SE6, SL5 |
| `src/sensemaking_skills/reasoning/` or `warrant_gate.py` imports change | SA6, SR1, SL6 |
| `distribution-drift.yaml` regenerated | SE10 |
| `test_path_drift.py` / `test_cli.py` go green (or gain failures) | SE2, SA10, SA12 |
| a new `experiments/` thread wires an import into `scripts/` or `src/` | SR1–SR4, SR-neg |
| `STATUS.md` / `CONTEXT.md` product-scope language changes | SA11, SA1 |
| retirement-plan doc-reconciliation items get done | SL7, SL8 |

If none of these has fired since the last refresh, the map is current — no work.

## 4. Safety conditions — when persistence would be UNSAFE

Do **not** promote the map to a persisted/consulted artifact if any of these
hold:

1. **The `MECH` refresh cannot be made to run cheaply** — e.g. `probe-repo.py`
   or `test_path_drift.py` becomes slow/flaky, so step 1/4 of §1 is not a
   seconds-level operation.
2. **`JUDG` rows exceed ~25% of the map** — too much of it is contestable to be
   a reliable shared reference.
3. **`JUDG` rows churn** — if a judgment row's reading flips more than once
   between refreshes, its semantics are not stable enough to write down
   (this is the repo's own `harden only where pressured` bar).
4. **The map starts being consulted *instead of* the recipe** — i.e. readers
   treat "no row for X" as "no issue with X" (the `SYNTHESIS.md` Q5
   silent-omission risk). Mitigation must be structural, not just a note: the
   map header must state, and a reader must see, "absence of a row means
   *not yet assessed*, not *fine* — use `ON-DEMAND-PROJECTION-RECIPE.md`".
5. **No owner has ratified persistence** — until then it stays an
   `experiments/` prototype.

## 5. Estimated maintenance cost

| Activity | Frequency (driven by §3 triggers, not calendar) | Cost |
|---|---|---|
| `MECH` refresh (steps 1-7 of §1) | on each triggering change; in practice a handful of times per active month | ~10-20 min, mostly waiting on `probe-repo.py` + two `pytest` selections |
| `JUDG` re-affirmation | only when a trigger plausibly touches a judgment row | ~5-15 min per affected row, a competent reviewer |
| `MIX` overlay review | when the mechanical half changes materially | ~5 min per row |
| full re-read for drift | once per quarter as a backstop | ~30 min |

The dominant cost is the `JUDG`/`MIX` overlay, ~14 rows total. That is the real
question persistence must answer: **is ~14 rows of periodically-reviewed
architectural judgment a burden the project will actually sustain?** V0/V1
cannot answer that; only real use over time can.
