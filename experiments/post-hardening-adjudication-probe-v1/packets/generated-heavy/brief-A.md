# Repository Sensemaking Brief — generated-heavy

## 1. Repository goal
`generated-heavy` is presented as a protobuf-based project: `README.md:3`
("Protobuf-based project.") is the entire stated purpose. The repository
combines three provenance categories — a committed "generated" protobuf
layer (`generated/`), a `dist/` build-output directory, and handwritten code
(`handwritten/`) whose entry point, `handwritten/main.py:1`, imports a
message type from the generated layer. In other words, the apparent goal is
a small Python service whose API schema lives in generated protobuf code and
whose build outputs are committed to the tree — but, as Sections 4 and 6
show, almost none of that machinery actually exists beyond the file names.

## 2. Current shape
The repository contains exactly six files (structural proof from recursive
`ls`):

```
generated-heavy/
├── README.md              (3 lines: title, blank, "Protobuf-based project.")
├── dist/
│   ├── app.py             (1 line: print('built artifact'))
│   └── bundle.js          (1 line: console.log('minified'))
├── generated/
│   ├── api_pb2.py         (3 lines: "Generated by the protocol buffer compiler.
│   │                       DO NOT EDIT!" header, class Message, pass)
│   └── api_pb2_grpc.py    (1 line: "# Generated. DO NOT EDIT!" header only)
└── handwritten/
    └── main.py            (4 lines: import Message, instantiate, print)
```

Notably absent (structural proof from `ls`): there is **no `.proto` file
anywhere**, no generation tooling (no Makefile, no `grpcio-tools` config, no
`protoc` invocation), no packaging metadata (`pyproject.toml`,
`setup.py`, `requirements.txt`), no tests, no CI, and no documentation beyond
the three-line README.

## 3. Strong signals
- **Layering intent is real**: `handwritten/main.py:1` imports
  `from generated.api_pb2 import Message` instead of redefining the message —
  the handwritten layer respects a generated/handwritten boundary, which is
  the correct shape for a protobuf project.
- **The generated-code convention is acknowledged**: `generated/api_pb2.py:1`
  carries the standard "Generated by the protocol buffer compiler. DO NOT
  EDIT!" header, signaling that the file is supposed to be treated as
  compiler output.
- **Clear provenance categories in directory names**: `generated/`,
  `handwritten/`, `dist/` communicate what each subtree is supposed to be,
  matching the subsystem split (generated protobuf layer, handwritten core,
  build output).
- **The handwritten entry point is runnable in principle**:
  `handwritten/main.py:1-4` imports, instantiates, and prints a `Message` —
  a working seam that would keep functioning if the generated layer were
  real.

## 4. Missing pieces
- **No `.proto` schema source**: the recursive listing shows zero `.proto`
  files, so the single source of truth a protobuf project must have does not
  exist. The generated layer cannot be regenerated, reviewed, or evolved.
- **No generation tooling**: nothing in the repository invokes `protoc` /
  `grpcio-tools` (no Makefile, no script, no dependency declaration), so
  even the *process* that is supposed to produce `generated/` is absent.
- **The gRPC module is empty**: `generated/api_pb2_grpc.py:1` contains only
  the header comment — a real generated `*_grpc` module would define service
  stubs; this one defines nothing.
- **The "generated" message is a hand-written stub**:
  `generated/api_pb2.py:2-3` defines `class Message: pass` with no fields,
  no descriptors, no serialization — none of the substance real compiler
  output would have.
- **The build outputs are placeholders**: `dist/app.py:1` and
  `dist/bundle.js:1` are one-liners with no corresponding build pipeline.
- **No tests, no packaging, no CI**: nothing verifies the handwritten layer
  against any schema, and nothing defines how the project is built or run.

## 5. Improvement opportunities
- Add an `api.proto` schema that actually defines `Message` (matching what
  `handwritten/main.py:1` imports), so the generated layer has a source of
  truth.
- Add a one-command regeneration step (Makefile target or script invoking
  `grpcio-tools`) and re-commit `generated/` from it.
- Either implement real gRPC stubs or delete the empty
  `generated/api_pb2_grpc.py:1` module so it stops implying a service
  surface that does not exist.
- Extend `README.md:3` from one line into a short explanation of the
  schema → generated → handwritten pipeline and of what `dist/` actually is.
- Add a CI check (or at least a local script) that regenerates
  `generated/` and diffs it against the committed files, so the
  generated/handwritten contract stops drifting silently.

## 6. Weakest boundary
The weakest boundary is the **contract between the files' claimed provenance
and their actual content** — specifically the "generated" protobuf layer.
`generated/api_pb2.py:1` declares it was "Generated by the protocol buffer
compiler. DO NOT EDIT!", and `generated/api_pb2_grpc.py:1` declares
"Generated. DO NOT EDIT!", but the bodies are a hand-written `pass` stub
(`generated/api_pb2.py:2-3`) and an empty module (`generated/api_pb2_grpc.py:1`).
No `.proto` source exists anywhere in the tree (recursive `ls`), so the
schema these files claim to encode cannot be found, reviewed, or regenerated.
Meanwhile the handwritten core anchors itself to this fabricated contract:
`handwritten/main.py:1` does `from generated.api_pb2 import Message`, so the
entire runnable surface of the repository rests on a stub whose real schema
is unknowable. The README (`README.md:3`) reinforces the illusion by calling
the project "Protobuf-based" without any protobuf definition present. The
`dist/` directory makes the same gesture at the build side:
`dist/app.py:1` and `dist/bundle.js:1` present one-liners as build artifacts
of a pipeline that does not exist.

Logic trace: `README.md:3` claims the project is protobuf-based; the only
protobuf-looking files are `generated/api_pb2.py:1` and
`generated/api_pb2_grpc.py:1`, both of which assert compiler provenance in
their headers; but the recursive file listing shows no `.proto` source and
no build tooling, and the file bodies are a `pass` stub
(`generated/api_pb2.py:2-3`) and a header-only module
(`generated/api_pb2_grpc.py:1`). The files therefore claim to be one kind of
artifact (compiler-generated, immutable, schema-derived) while actually
being another (hand-authored placeholders with no schema anywhere) —
precisely the "file claims to be one format but is actually another" pattern
of Contract Mismatch. `handwritten/main.py:1` depends on that mismatch, so
the handwritten layer's contract is anchored to a schema that exists
nowhere.

**Weakness type:** Contract Mismatch

## 6.5. Problem classification (fog type)
**architecture_fog** — the primary uncertainty is structural: the
generated/handwritten/build boundary is fabricated and unenforced, and the
schema source of truth is missing. This is a code-structure and boundary
problem, not a product, UI, or documentation problem.

- Not `ui_fog`: per the UI Fog Signals Registry decision tree, the first
  question is "does the codebase have frontend/UI code?" The only JS file,
  `dist/bundle.js:1`, is a one-line placeholder inside a build-output
  directory — there are no views, no routing, no components, no design
  system. Answer: not `ui_fog`.
- Not `product_fog`: no user-need or feature-requirement question is at
  stake; the repository goal, however thin, is stated (`README.md:3`).
- Not `docs_fog`: the README is thin, but the *defect* is not missing
  prose — it is that the code artifacts themselves misrepresent their
  contract. Better documentation would not repair a `pass` stub presented
  as compiler output.

## 7. Evidence
The diagnosis rests on the following cited observations:

1. `generated/api_pb2.py:1` — the file's own header asserts it was generated
   by the protocol buffer compiler and must not be edited.
2. `generated/api_pb2.py:2-3` — the file's entire content is
   `class Message:` / `pass`: no fields, no descriptors, no serialization
   logic, i.e. not compiler output by any measure.
3. `generated/api_pb2_grpc.py:1` — the gRPC module is a single header line
   with zero stubs, yet claims "Generated. DO NOT EDIT!".
4. `handwritten/main.py:1` — `from generated.api_pb2 import Message` ties
   the handwritten layer to the stub as if it were a real schema.
5. `README.md:3` — "Protobuf-based project." is the only documentation and
   the only place the protobuf claim is made.
6. `dist/app.py:1` and `dist/bundle.js:1` — one-line placeholders presented
   as build artifacts.
7. Structural absence: recursive `ls` of the fixture shows no `.proto` file
   and no generation/build tooling anywhere in the repository.

Logic trace: the headers at `generated/api_pb2.py:1` and
`generated/api_pb2_grpc.py:1` establish the files' claimed contract
(compiler-generated, immutable); the bodies at `generated/api_pb2.py:2-3`
(a bare `pass` stub) and `generated/api_pb2_grpc.py:1` (header only) prove
the actual content is hand-authored placeholder code; the recursive listing
proves there is no `.proto` source or tooling that could have produced
either file. Claimed artifact type and actual artifact type therefore
diverge in the same file pair, which is the definition of Contract Mismatch.
Because `handwritten/main.py:1` imports from that pair, every consumer of
the handwritten entry point inherits the mismatch, making it the weakest
boundary of the repository.

## 9. Why this boundary matters
Every consumer of this repository is misled in a way that compounds:
contributors and agents treat `generated/` as immutable truth and therefore
never question the schema, while the schema literally does not exist — the
API shape is unknowable from the repository. Schema evolution is impossible
(no `.proto` to edit and regenerate), so any real protobuf work means
rewriting the generated layer from scratch and silently breaking the
contract `handwritten/main.py:1` was written against. The committed `dist/`
placeholders teach readers that build outputs are not trustworthy, and the
empty `generated/api_pb2_grpc.py:1` implies a gRPC service surface that
would not exist at runtime. For a project whose entire premise is
"protobuf-based", a fabricated generated layer is the whole value
proposition at risk.

## 10. Candidate next steps
1. Write the missing `api.proto` schema defining `Message` (matching the
   import at `handwritten/main.py:1`), establishing the source of truth.
2. Add generation tooling (a Makefile target or script invoking
   `grpcio-tools`) and regenerate `generated/` so the committed files match
   their own "DO NOT EDIT" headers for real.
3. Remove or properly implement `generated/api_pb2_grpc.py` so the
   repository stops advertising a gRPC surface it does not have.
4. Replace or delete the placeholder `dist/app.py:1` / `dist/bundle.js:1`
   and document what `dist/` actually is in `README.md`.
5. Add a regeneration-sync check (CI or local script) that diffs freshly
   generated output against the committed files, closing the drift loop.

## 11. Recommended next step
Write the missing `api.proto` defining `Message` — the smallest change that
creates the source of truth the entire repository pretends to have. Every
other repair (regeneration tooling, real gRPC stubs, honest `dist/`, sync
checks, README) depends on a schema existing first, and
`handwritten/main.py:1` already tells us the one type it must contain.
