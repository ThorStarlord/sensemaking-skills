# Strategic Evolution & Learning v1 — Optional Portable Agent Guide

**Use selectively, not as a new mandatory phase.** This guide is for a coding agent confronting (A) an *open, material future-direction choice* for a repository/system or (B) a *consequential new observation or insight* whose relationship to prior explicit knowledge deserves interpretation. It can also support a bounded conceptual inquiry outside a complete Level-3 analysis when a real strategy decision is **not** open.

**The two independent questions:**

- **Strategic Evolution Analysis:** Where should this system evolve, and why? Compare coherent future outcomes/capabilities, source-grounded mechanisms and meaningful alternatives under current governing intent.
- **Learning & Reassessment:** What did we learn, and what changes—if anything? Relate specific prior understanding to actual new evidence, changed interpretation or owner intent, and identify limited consequences without automatic strategy mutation.

**Results:** a source-grounded `StrategicEvolutionRationale` or `LearningAccount` (possibly sections of existing reports), a clear `NO_CHANGE` / `NO_MODEL_CHANGE` / `NO_SELECTION` / `NOT_ASSESSED`, or a properly scoped handoff to the *existing* strategic/reconciliation/owner capability. These are **documentary roles**, not new parsed artifact IDs, skills, machine enums, graph predicates or autonomous controller stages.

**Portable by design:** target repositories need no `.sensemaking/`, ADR 0031, `CONTEXT.md`, Sensemaking CLI, query index, prior ontology docs, or extra installed optional Skills. Always begin with target-owner intent/current source/decision. Optional reviewed knowledge is a defeasible source pointer; source-only reconstruction is valid.

## 1. Establish the actual question and stop boundary

**Is the system's future materially open?** If no, do not redo the full strategic exploration merely because a new idea can be imagined. A local repair or already authorized feature can be executed directly under the user's actual authority. If the user requested *possibilities only*, report possibilities, not a new selected Level-3 work plan.

**Has material learning actually returned?** If no prior explicit meaningful claim/assumption/lesson or evidence-bearing result exists, do not create a learning account as ceremony. A useful current source summary or direct engineering response may suffice.

**What is the governing context?** Identify original user-supplied end, beneficiaries, accepted product outcomes and non-goals, actual source revision, authority to inspect versus act/merge/release/change goals, and precisely which decision is at stake. Owner change cannot be inferred from an agent's attractive hypothesis.

**Evidence distinction:** observed current source or behavior; source-quoted historical fact; derived conditional; inferred interpretation; future/cause hypothesis; purpose-relative evaluation; actually authored strategic selection; separately authorized execution; verified downstream/user outcome. Report each at its own claim ceiling.

When a durable strategy output is warranted, use the *existing available* `strategic-repository-analysis` Skill/`strategic_repository_analysis` contract, rather than treating this view as a new producer. When material returned evidence must be compared to a prior dated Level-3 analysis, use the *existing available* `strategic-repository-reconciliation` capability and current `strategic_reconciliation` contract. Never forge or silently omit producer requirements if not installed/available.

## 2. Profile A — Strategic Evolution Analysis

**Trigger:** a consequential future-direction choice where current capabilities, limits and plausible alternative user experiences, product outcomes or architectural paths might change what should be pursued. Examples include "what should this repository become?" or "which strategic capability creates value now?" Do not activate for an isolated code patch or a familiar extension that serves already settled work.

### A. Start with a source-grounded current system

- Source the intended user/beneficiary, problem, governing outcome and owner/product boundary.
- Model the *real existing* software/product capabilities, dependency/contract/authority boundaries and important limitations at the inspected revision. A documentation claim may be partial or stale; source only what matters to the decision.
- Determine whether a stated milestone/proxy could be satisfied while its underlying desired end remains unmet. Preserve owner wording; identify goal-fit tension instead of replacing intent.
- State the **Strategic Decision to Support**, not merely a list of issues.

### B. Differentiate types of opportunities

Before comparing, classify the *future-state meaning*:

| Type of potential evolution | In scope when | Must not be called |
| --- | --- | --- |
| **Distinct desirable end** | A previously unstated user/beneficiary outcome becomes plausible from real constraints/relationships | An accepted requirement or demonstrated user demand without explicit evidence/owner authority |
| **New capability serving known end** | Changes what the product/system can do for an accepted goal | A different primary goal merely because mechanism is new |
| **Architecture/mechanism change** | Another coherent way to realize a capability/end, including source-grounded alternatives | A product end, observed implementation or selected architecture |
| **Simplification/consolidation/retirement** | Removing duplication, overhead or harmful behavior better serves the end | Stagnation merely because less machinery is proposed |
| **Bounded repair/maintenance** | Real defect/contract issue worth fixing without material strategic future change | Strategic Frontier admission by default |
| **Thesis-level redefinition** | A beneficiary/problem/JTBD or major product boundary is genuinely challenged | A Level-3 ratified decision without actual Level-4 owner authority |

A new graph relation, idea label or source pointer is **not** automatically a new product capability or strategically distinct option. Another plausible future can remain a `ProductPossibility` *hypothesis*, not a selected end.

### C. Make plausibility and tradeoffs explicit

For each material alternative, connect:

```text
governing purpose + source-grounded present capability/limit
 -> plausible desired future/end
 -> capability transition / architecture mechanism / constraints
 -> assumptions and conditional consequences
 -> beneficiaries, upside, failure path, omission/deferral cost
 -> qualitative comparative judgment under THIS purpose
 -> possible reason to reconsider
```

Use a source-qualified existing `ConstructionPath`, `ArchitectureOption` and `ConsequenceHypothesis` only if those existing typed identities really apply. A speculative chain is **not transitive proof** that an architectural option causes valued user benefits. Counterfactuals are useful when they can change the decision: absent beneficiary demand, changed source authority, no actual consumer, alternate simpler implementation, inability to load the guidance, or a source-only agent reaching an equally strong result.

Evaluate plausible alternatives by **mission alignment, meaningful outcome, dependency, evidence, downside, reversibility, maintenance, commission and omission/deferral**, without numeric ranking or forced option counts. Inquiry priority, relative strategic attractiveness and implementation priority are different judgments.

### D. Synthesize without overclaiming

State what is warranted *under current purpose and authority*: a promising direction, conditional preference, further bounded inquiry, deferred option, zero coherent paths, no change, owner decision or genuine Level-4 thesis review. Preserve *credible discarded options and their reconsideration hinges* rather than rewriting history as though they never existed.

For real Level-3 analysis, its canonical artifact/author keeps responsibility for current strategic outcome and paths. A recommended `BUILD` responsibility **is not implementation authorization**, and newly learned opportunity **is not a ratified ProductPossibility**. A Level-4 question may be analyzed/packaged for the owner but cannot be silently decided.

**Useful short documentary view:** "At source R, under goal G for beneficiary B, observed capabilities C and limit L make future F plausible through mechanism M if premise P; alternatives A/D have these costs and omission implications; thus direction X is conditionally preferable / none is selected for purpose Y; revisit when E occurs; actor/authority boundary Z."

**Stop:** source-backed alternatives and why/why-not-now are sufficient, no material future choice is open, evidence makes a claimed benefit unassessable, or the next needed judgment is reserved for a different actor. An additional possibility count does not create evidence.

## 3. Profile B — Learning & Reassessment

**Trigger:** consequential returned evidence, later source/currentness discovery, new argument, actual owner choice or cross-episode comparison could change a *specific prior explicit understanding*. A one-off successful local edit need not create a historical lesson or new document.

### A. Identify predecessor, source and object of change

Name the **exact earlier claim, assumption, decision, uncertainty, lesson, preference or source interpretation**, author/recorded revision and why it mattered to the decision. Then name the new observation/interpretation/owner input, its actual source and currentness.

Distinguish three **non-machine descriptive lenses**:

- **WORLD_CHANGED:** actual system/behavior/source world was altered (e.g., verified code changed). Do not infer product outcome or strategy changed.
- **UNDERSTANDING_CHANGED:** an existing system fact, historic incident or prior alternative was wrongly interpreted, unseen, poorly framed, stale or context-limited. Do not falsely credit new construction for discovering already existing capability.
- **GOVERNING_INTENT_CHANGED:** an actually identifiable owner or authority has ratified another product problem, beneficiary, goal or scope. Do not reclassify the agent's creative idea as owner intent.

These can coexist; identify exactly which sources support each. **Source file drift** alone establishes neither meaning changed nor a new strategic direction; source content/currentness should be inspected.

### B. Attribute what learning actually establishes

Explain *why* the new material affects the predecessor's specific premise or decision. Separate observation from inference, counterfactual, evaluation and hypothesis. Identify unchanged nearby claims. Do not rewrite an earlier analysis's historical evidence merely because the current interpretation differs.

Use the existing Learning/Reconciliation dispositions where they genuinely apply: `NO_MODEL_CHANGE`, `CONFIRM`, `REVISE_CLAIM`, `RESOLVE_UNCERTAINTY`, `OPEN_NEW_UNCERTAINTY`, `CHANGE_RESPONSIBILITY`, `CONTINUE`, `STOP`, `ESCALATE`, `REOPEN_STRATEGY`, `THESIS_REVIEW_REQUIRED`. These belong to the **existing policy**, not a newly minted LearningAccount machine schema. A material `NO_MODEL_CHANGE` may be more accurate than a synthetic new ranking.

**Source-to-decision output:** "Prior dated claim X said P under conditions C. New source Y shows Z / suggests H, so revise/narrow/confirm X exactly in this scope. A, B and earlier source history stay unchanged. The current bounded responsibility/strategy remains / changes in the following named way. Next re-entry condition is E; owner authority boundary is Q."

### C. Distinguish three learning scopes

**Episode/responsibility:** one current claim, assumption, test/repair or next action. Keep a paragraph in PR/receipt if materially useful for later work; no universal learning log.

**Repository/longitudinal:** a dated, source-linked history of earlier analysis, later changed evidence and its interpretation. Use existing Strategic Continuity / `strategic_reconciliation` when materially affecting an identifiable earlier Level-3 analysis, without overwriting it or adding new fields.

**Cross-repository/capability doctrine:** several *genuinely comparable* episodes may suggest a reusable Sensemaking guide/policy improvement. Compare actually different causal mechanisms, source revision and owner conditions; look for counterevidence, independent heterogeneity, applicability/transfer limits and minimum useful guidance change. One striking incident or several related PRs in the **same repository** are normally not a universal engineering doctrine. The doctrine change is a **candidate**, not automatically written to public Skill text, and still needs actual scope/qualification authority.

### D. Historical lesson usefulness is not retrieval

Distinguish **retained** -> **retrieved** -> **source-checked** -> **materially decision-informing (accepted/narrowed/rejected)** -> **outcome-supported** -> **independently reused** -> **comparatively beneficial**. A stored lesson and passing index lookup do not show it helped an agent. A historical lesson can be fully true in its original context and misleading in another one; source-grounded **rejection** is often the correct action.

**Learning can expand future questions**: a corrected framing may expose a different desirable product end. State its possible beneficiary, mechanism and value hypotheses, but do not convert it into user demand, a chosen strategic path or product-thesis change. Re-enter Strategic Evolution Analysis only when a *material present Level-3 future-direction question* genuinely becomes open.

**Worked bounded example (illustrative, not observed here):** A historical report claims an authored knowledge context can always be recalled. A later source reading shows its host only loads selected Skills. The correct learning is **narrow original retrieval-applicability premise**; if the current strategy still prefers source-grounded agent-native recall, the strategic direction may remain unchanged, while a bounded documentation/consumer repair becomes worth assessing. Do not declare either "knowledge has no value" or "build a mandatory context runtime."

**Worked rejection (illustrative):** a lesson from a file-ownership-based `context-for` query suggests adding an exact `owned_paths` link. A different repository's consumer reads all files directly and has no ownership filter. The later agent should source-check and **reject that mechanism's applicability**, not fabricate a graph defect or update universal Skill policy.

### E. Decide what changes and where it belongs

When only a specific dated comparison changes, the existing **Convergent Reassessment / AssessmentRevisionAccount** meaning applies; leave unaffected portfolio members and different-purpose priorities alone. When materially returned evidence changes a prior **strategic_repository_analysis**, use the existing `strategic-repository-reconciliation` producer. When evidence challenges a ratified owner product thesis, request/prepare a valid Level-4 decision instead of claiming one. **LearningAccount itself is not a second producer of any of these artifacts.**

**Stop:** sufficient explicit delta/limits are reconstructible; no decision-relevant change is supported; lesson is inapplicable; verification would require unrelated evidence; or actual owner/host authority is required. `NO_MODEL_CHANGE`, not storing a new artifact, and no new question are valid successes.

## 4. Relationship to other conditional inquiry profiles

The current Sensemaking reference ecosystem already covers divergence/possibility coverage, consequence depth, dated Convergent Reassessment, adversarial challenge, architecture/product design, existing Level-3 Strategic Analysis and Strategic Reconciliation. This guide **clarifies the connective meaning**, not replaces those producers or requires them to run.

Possible, non-mandatory returns:

```text
source-grounded desired future question
 -> future-direction rationale if strategy is genuinely open
 -> further inquiry / source checking / ordinary bounded execution
 -> consequential new information
 -> learning account (exact delta, preserved past, claim ceiling)
 -> local unchanged/changed responsibility
    OR specific dated judgment reconsideration
    OR existing Level-3 strategic reconciliation
    OR Level-4 owner review
    OR new hypothetical question
    OR stop
```

Do **not** force another full strategic breadth/funnel because a local implementation succeeded or file hash changed. Do not create a generic Learning Engine, new `StrategyState`, `BeliefState`, doctrine-memory schema, fixed workflow stage, numeric scores, causal proof engine or public Skill from these documentary roles.

The [optional record template](strategic-evolution-learning-record-template.md) exists only for consequential contexts where concise source-linked prose would lose an important future decision. It is not required and cannot replace canonical strategy/reconciliation/PRD/architecture outputs.

## 5. Minimal re-entry and evidence claims

When a later agent uses this guide, it should identify original source/assessed revision, relevant authority, exact strategy or learning target, current evidence, what remains hypothetical, and a reasoned stop/change. A valid recorded reason can be **NO_CHANGE**. Prefer the original source and existing reviewed index over copy-pasted interpretations where currentness matters.

**Evidence ceiling:** authored guide exists != installed in particular host != loaded by host != read/invoked != correctly applied != useful for independent later decisions. Hosted distribution may show installability but not semantic benefit. A successful source-linked analysis is not a proof that graph knowledge improves creativity or strategic selection over a capable source-only agent. Never claim new user end ratification, deployment or protected action from this guidance.


## Optional premise-focused source re-entry

For a particular historical premise whose applicability may have changed, use [Premise-Sensitive Reconsideration](premise-sensitive-reconsideration-v1.md) when material. It preserves the existing strategic reconciliation/learning owner and distinguishes navigation links from decision-bearing grounds. A missing graph or viewer is not an obstacle to a source-grounded answer.
