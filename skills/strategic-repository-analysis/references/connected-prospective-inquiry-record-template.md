# Connected Prospective Inquiry — Optional Documentary Record

**Use sparingly.** This is a suggested layout for a consequential inquiry that must survive another agent/context; it is **not** a registered artifact, validator contract, machine schema, required stage sequence, PRD, architecture selection, or owner decision. For a small task, source-linked prose or an existing PR/ADR/report is sufficient. See the [portable guide](connected-prospective-inquiry-v1.md).

**Delete sections that were not warranted** instead of adding empty boilerplate. A factual source with an identifiable revision is stronger than a confident unsourced answer. Preserve original typed IDs; never invent `poss:`, `arch:` or `conseq:` records merely to complete a template.

**Never infer:** `A may B` and `B may C` prove `A causes C`.

## B. Convergent Reassessment, if warranted

**AssessmentRevisionAccount R1 — Prior source:** actual earlier `AssessmentJudgment` / `PortfolioSnapshot` / `ProvisionalPreference` / authorized decision, its author/date, original frame, operand IDs and earlier source revision.

**New grounds:** a specific new consequence/assumption/evidence and exactly which criterion it affects.  
**Comparison purpose:** inquiry priority / product attractiveness / authorized implementation / other explicit frame; confirm prior question is comparable.  
**Actual revised interpretation:** `NO_CHANGE` / same preference with narrowed scope / same order with different reasons / local pairwise change / incomparable or insufficient evidence / authority-appropriate sourced decision reconsideration. These are documentary descriptions, not a new machine enum.  
**Unaffected alternatives and earlier record:** original sources retained, list what did not change.  
**Reversal / re-entry:** source, assumption, actor or beneficiary change that could alter this interpretation.  
**Not inferred:** new preference is not owner adoption or permission to implement.

## C. Adversarial Review, if warranted

**ChallengeResponseAccount X1 — Exact target/source:** identify a *real proposition or design element*, its scope/currentness and epistemic type.

- **Objection and failure pathway:** What exactly would make this target invalid or misleading?
- **Grounds:** source-observed counterevidence / disputed interpretation / hypothetical scenario / insufficient evidence (separately labeled).
- **Impact if sustained:** affected conclusion, contract, beneficiary, choice or authorization.
- **Response and grounds:** rebuttal, accepted correction, narrower claim, changed proposal, bounded inquiry, tolerated risk or unresolved issue.
- **Does the response really answer this target?** Explain why or acknowledge it does not.
- **Residual and follow-on consequence:** what cannot be claimed, and what evidence/authority would be needed for repair verification or a different choice.

**Not inferred:** hypothetical critique is not an observed defect; proposed repair is not verified closure; critic does not grant or revoke owner authority.

**Coherence:** dependencies, contract ownership, actual versus proposed components, alternatives retained, adverse effects and incompatible goals.  
**Open premises:** further source inspection, owner intent, empirical evidence or technical contract required.  
**Actual decision and authorization status:** recommended only / explicitly selected within documented authority / owner-reserved / no coherent proposal; separately state whether build is authorized.  
**Stop/return:** what the active agent may inherit and what must not be executed.

## Compact worked illustration (NOT an observed case)

Suppose a source-readonly engineering inquiry compares A (selective, agent-requested knowledge context) and B (context injected by a runtime). A looks preferable for host independence. A later observation **would be needed** to know whether the agent actually used it. A challenge might target host loading, with an answer of "retain a source-file fallback and record invocation as unassessed." The preference could remain A **with a condition**, while the proposed design says only what source-based behavior ought to exist. No new owner target, mandatory runtime stage, PRD, tested benefit or committed feature follows from this illustration.

## Closing integrity check

- Original identity, source and assessed revision preserved?
- Mechanism and counterfactuals stated without inventing causation?
- Earlier judgment kept historical; changed versus unchanged named?
- Challenge target, grounds, response and residual distinct?
- Design elements trace to actual goal and constraints?
- Recommendation, selection, authority, implementation and verification separate?
- Reason to stop or to inquire further actually grounded?
- Real producer/consumer contract reused when an artifact is required?
- Could another agent reconstruct this from source without this chat?

**Documentary closure is not product or empirical closure.** Archive only the meaning another context truly needs.
